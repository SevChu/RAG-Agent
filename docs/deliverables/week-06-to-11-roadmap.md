# 第 6～11 周及后续研发路线与 GitHub 版本节点

## 路线定位

项目暂不进入最终交付与答辩阶段。原第 6 周计划日 4～5 的 Docker、演示材料、发布候选和最终
验收整体后移到“最终交付周”；第 6～11 周依次推进评分算法、AgentProfile、微调平台、首次真实
微调、动态长上下文、资料空间记忆和自有金标集基础。每周仍保留自动测试、数据隔离和可复现性检查，不能把质量门一起后移。

当前应用界面、系统提示和面向用户的错误信息仅支持中文。英文 README 只解决 GitHub 项目说明的
可读性，不代表产品已经国际化。中英文产品支持作为 `v1.5.0` 之后的独立 `v1.6.0` 里程碑推进，
避免与评分算法、微调、记忆和金标集阶段混在同一验收范围内。

基础功能已发布为 `v1.0.0`；第五周的 FiQA、RAGTruth、RAGBench、统一 Dataset Adapter 和
baseline profile 1.0.0 已发布为 `v1.1.0`。随后以 `v1.1.1` 单独修正专有许可与第三方材料边界，
不移动旧 Tag，也不改变 v1.1.0 的功能和 Benchmark 数值。

## 版本策略

- 遵循 Semantic Versioning；兼容新增使用 minor，修复使用 patch，破坏 API/数据库兼容才使用 major。
- 计划版本不等于已经发布；只有完成验收、全量回归、隐私检查、版本元数据同步并获得用户批准后，
  才创建提交、Tag、推送和 GitHub Release。
- 已发布 Tag 不移动、不覆盖；候选阶段发现问题时继续修复，不重写旧 Tag。
- 公开仓库只包含代码、配置模板、哈希和汇总指标，不上传公开数据集副本、资料空间、对话、数据库、
  模型权重、训练样本、预测明细或 API Key。
- 预发布训练平台使用 `-beta.N`；真实训练闭环通过后再发布同一 minor 的稳定版。

## 第 6 周：评分与检索算法优化（目标 `v1.2.0`）

### 计划日 1：实验注册与错误切片

- 状态：已于 2026-08-31 完成；见[计划日 1 记录](week-06-day-01.md)；

- 统一 per-domain、正负类、长度、证据数量和错误类型切片；
- 所有优化只读取 train/validation，不重新利用 test 调参。

### 计划日 2：Dense Top-100 直接重排

- 状态：已于 2026-09-01 完成；见[计划日 2 记录](week-06-day-02.md)；
- 使用现有 BGE-M3 Dense Top-100 和现有 BGE Reranker；

- 守门条件：Recall@100 不低于 Dense 1.1.0，单列 nDCG@10、MRR、延迟和显存。

### 计划日 3：Completeness 评分改进

- 状态：已于 2026-09-04 完成；见[计划日 3 记录](week-06-day-03.md)；
- 先尝试 relevant → utilized → completeness 两阶段建模；
- 再比较线性、树模型或校准，不在同一实验同时更换特征和模型；
- 主要指标为 RAGBench validation Completeness Spearman/RMSE，其他三项不得显著退化。
- 两阶段候选通过形式门，但领域 bootstrap 95% CI 覆盖 0，暂不冻结为默认。

### 计划日 4：NLI 幻觉定位

- 状态：已于 2026-09-04 完成；见[计划日 4 实施报告](week-06-day-04.md)；NLI 候选通过
  validation 数值门与 source-cluster bootstrap 稳定性门，进入 Day 5 评审；
- 先审查适合句子级 entailment/contradiction 的开源模型、许可、大小和显存；
- 新模型下载前单独提交审批；
- 在 RAGTruth validation 上比较 AUPRC、回答级 Recall 和 span char F1。
- span char F1 `0.228140 → 0.243289`，但 span recall 下降；尚不冻结为默认，官方 test 继续封存。

### 计划日 5：冻结 1.2.0 候选

## 第 9 周：首次真实微调（目标 `v1.4.0`）

1. 优先选择小型 Scorer 或 Reranker，不直接以生成大模型 LoRA 作为第一轮；
2. 审批 base model、许可、下载大小、训练数据、显存/时间和外部成本；
3. 固定未微调 base model 对照，只在 train/validation 调参；
4. 将训练产物登记为 Adapter，比较质量、稳定性、时延、显存和回滚；
5. 用户批准后执行一次 test，将通过的 Adapter 绑定到指定 AgentProfile，但不自动设为全局默认。

生成模型逐智能体 LoRA/QLoRA 等自有训练数据与目标稳定后再进入后续 minor 版本。

## 第 10 周：动态长上下文与资料空间记忆（目标 `v1.5.0`）

### 计划日 1：上下文能力与基线

- 将旧“课程记忆”设计迁移为通用资料空间语义；
- 建立当前 6 条/6000 字符基线和模型上下文能力表；
- 固定 M0/M1/M2 对照、Token、延迟、长程指代和空间泄漏指标。

### 计划日 2：动态 Token 预算与历史选择

- 按模型窗口、系统指令、当前问题、检索证据、输出预留和安全余量分配历史预算；
- 优先保留最近原文，较早历史使用滚动摘要与相关片段；
- 未知模型或估算异常时保守降级，不直接向用户暴露上游 context-length 错误。

### 计划日 3：资料空间记忆后端

- 新增记忆实体、来源、状态、重要性、替换关系和生命周期迁移；
- 支持候选、确认、编辑、停用、删除和全部清空；
- 记忆只允许绑定一个资料空间，不作为资料事实引用。

### 计划日 4：记忆读取与安全边界

- 查询同时验证资料空间归属，并限制条数和独立 Token 预算；
- 快速对话、其他资料空间和外部网页不得自动写入；
- 提取或读取失败时降级为无记忆模式，不阻断普通 RAG。

### 计划日 5：前端控制与隔离验收

- 增加记忆开关、列表、来源、编辑、删除和清空入口；
- 报告本次使用条数而不暴露内部提示；
- 跨空间泄漏、停用后使用、删除后使用的容忍值均为 0。

## 后续国际化里程碑：中英文产品支持（目标 `v1.6.0`）

该阶段在 `v1.5.0` 收口后启动，具体自然周由前序研发进度决定。英文 README 已先行建立，用于
公开仓库说明；产品本身仍按“仅中文”标记，直到以下五个计划日全部通过验收。

### 计划日 1：国际化基础与语言契约

- 建立前端 locale 资源目录、稳定翻译键、默认语言和缺失翻译回退规则；
- 评估并审批 `vue-i18n` 或等价依赖，不在未审查时直接引入；
- 保存用户语言偏好，并定义首次访问、浏览器语言和手动切换的优先级；
- 后端错误由稳定 error code 与本地化 message 分离，避免前端依赖中文字符串判断业务状态；
- 明确 `zh-CN` 为默认及最终回退语言，未知 locale 不导致请求失败。

### 计划日 2：英文界面与用户可见错误

- 翻译导航、资料空间、智能体对话、设置、上传、索引、总结、组卷和评测主路径；
- 覆盖空状态、表单校验、确认框、加载状态、失败提示、日期/数字和可访问性文本；
- 检查英文文本变长后的响应式布局、表格、按钮、移动端和流式回答界面；
- 建立硬编码中文扫描，只允许数据正文、引用原文和明确登记的专有名称保留原语言；
- 用户切换语言时不清空会话、不重建资料空间，也不改变模型或检索配置。

### 计划日 3：提示词、生成策略与语言隔离

- 为问答、总结、组卷、联网、拒答和验证节点建立版本化中英文提示模板；
- 默认跟随用户选定语言回答，同时允许引用保持资料原文并标注语言差异；
- 明确中文界面下英文问题、英文界面下中文问题及混合语言问题的行为；
- 错误回退不得把内部提示、环境变量、模型路由或未翻译键暴露给用户；
- 提示模板与 AgentProfile revision 绑定，语言切换不能静默改变已冻结实验配置。

### 计划日 4：英文资料与 RAG 能力验证

- 建立英文 PDF、PPTX、DOCX、Markdown、TXT 的解析、OCR、分块、引用和拒答用例；
- 验证英文缩写、同义词、专有名词、数字/表格、跨文档和长上下文检索；
- 增加中文查询检索英文资料、英文查询检索中文资料的跨语言切片；
- 不自动翻译或覆盖用户原始资料，翻译只作为显式生成能力并保留原文引用；
- 分别报告中文、英文、跨语言和混合语言质量，不能用合并均值掩盖单一语言退化。

### 计划日 5：双语回归、文档与 `v1.6.0` 候选

- 前端对两种语言运行组件、主流程、语言切换和视觉回归；
- 后端覆盖 locale 解析、稳定 error code、SSE、提示模板、会话恢复和回退行为；
- 冻结中文、英文、跨语言三类评测切片，按语言分别报告检索、忠实性、引用和拒答；
- 补齐英文 Quick Start、配置、API、运行排障和安全边界文档，术语与中文版本保持映射；
- 完成隐私、许可、密钥、数据隔离和中文能力回归后，交由用户决定是否发布 `v1.6.0`。

### 国际化验收边界

- 英文 README 存在、底层模型能用英文回答或 OCR 能识别英文，都不等同于产品英文支持完成；
- 两种语言必须共享同一业务能力，不允许英文界面隐藏失败功能来通过验收；
- 中文现有主路径不得因国际化发生实质性退化；具体允许波动需在实施前按冻结基线定义；
- 外部数据集或模型的语言、地域与许可适用范围必须单独记录；
- 未翻译内容必须安全回退并可观测，不能显示翻译键或静默丢失操作说明。

## 每个 GitHub 版本的固定发布门

1. 用户明确验收本节点并批准提交/推送；
2. 后端测试、Ruff、Mypy 和前端测试、类型、Lint、构建通过；
3. 数据库迁移、OpenAPI、关键浏览器路径和向后兼容验证通过；
4. 数据、模型、缓存、预测、资料、对话、数据库和 Key 均未进入 Git；
5. `backend/pyproject.toml`、`backend/uv.lock`、FastAPI、前端 package/lock、CHANGELOG 同步；
6. Release Notes 记录功能、实验结果、数据/模型身份、限制和升级方式；
7. 创建不可变 annotated Tag，并在用户批准后推送 GitHub。
