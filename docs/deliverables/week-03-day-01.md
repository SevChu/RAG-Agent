可能过期的向量。

## 检索接口

```http
POST /api/courses/{course_id}/retrieval/search
Content-Type: application/json
```

最小请求：

```json
{
  "query": "栈和队列的主要区别是什么？",
  "top_k": 5
}
```

可选使用 `document_ids` 将检索限制在不超过 50 份已完成资料中。`top_k` 允许 1～20，
日 1 人工验收固定使用 5。

响应会返回：

- 排名、余弦相似度和完整 Chunk 文本；
- 原文件名、文件类型、章节路径；
- PDF 页码、PPTX 幻灯片号或文本行号；
- 本次纳入搜索的资料数、实际命中数、Embedding 设备和耗时；
- 明确的 `retrieval_mode=dense`，便于后续与重排、混合检索做对照。

开发服务启动后可在 `http://127.0.0.1:8000/docs` 直接调用，无需手写命令。

## 人工抽查不是“总共只看 5 条”

计划日 1 建议准备 **5 个代表性问题，每个问题检查 Top-5**。最多查看 25 条结果，但无需
逐字校对每个 Chunk，重点判断下列事项：

1. Top-5 中是否至少有一条能支持回答；
2. 第一条相关结果排在第几名；
3. 文件名、章节路径、页码/幻灯片号是否可追溯；
4. 是否混入其他课程或未完成资料；
5. Chunk 是否语义完整，是否出现明显跨章节拼接。

如果只是先确认接口能工作，可执行 5 个问题 × Top-3 的冒烟抽查；这不能替代正式的
Top-5 验收。

## 验收后新增体验改进：显示真实处理进度

用户于 2026-08-03 补充提出：文件上传完成并进入“处理中”后，资料列表应在状态下方显示
处理进度条和百分比，避免只能等待 `processing → completed/failed` 而无法判断当前进展。
该项记入计划日 1，作为**待实现的验收后体验改进**；它不改变已经通过的 Dense 检索验收结论，
完成后再单独回归验收。

这里必须区分两个不同进度：

- **上传进度**：浏览器把文件传给后端的网络传输进度，现有上传弹窗已经支持；
- **处理进度**：后端执行解析/OCR、结构化分块、Embedding 和 Qdrant 写入的索引进度，当前尚未提供。

计划采用后端持久化的真实阶段进度，而不是前端定时模拟增长：

| 处理阶段 | 建议进度区间 | 计算依据 |
|---|---:|---|
| 等待任务/准备 | 0%～5% | 任务已创建、文件与运行环境检查完成 |
| 解析或 OCR | 5%～55% | 已处理页数、幻灯片数或文本块数 / 总数 |
| 结构化分块 | 55%～65% | 已生成并校验 Chunk |
| Embedding | 65%～92% | 已向量化批次 / 总批次 |
| Qdrant 写入与收尾 | 92%～99% | 已写入批次、旧向量替换和一致性收尾 |
| 已完成 | 100% | 数据库状态已经提交为 `completed` |

区间权重是对不同处理阶段的可解释估算，不等于精确剩余时间；页面同时显示“正在 OCR
第 18/120 页”或“正在向量化第 3/8 批”等阶段信息，比单独显示百分比更能解释耗时。

实现拆分：

1. 文档记录增加处理百分比、处理阶段和可选阶段明细，并通过资料列表/状态接口返回；
2. 解析器、OCR、分块、Embedding 和向量写入在真实处理节点上报进度；
3. 进度更新保持单调且做节流，避免逐页/逐 Chunk 频繁写 SQLite；
4. 前端沿用现有 2 秒活动任务轮询，在“处理中”标签下显示进度条、百分比和阶段文案；
5. `completed` 必须为 100%；`failed` 不伪装成 100%，应保留最后阶段并继续显示失败原因；
6. 应用重启恢复任务时回到明确的“等待重新处理”状态，不能展示已经失效的旧进度。

补充验收标准：刷新页面后进度不丢失；多个文件各自独立显示；处理中的百分比不倒退；
完成与失败状态准确；慢速扫描 PDF 可以观察到页级 OCR 进展；现有上传进度、重试、删除和
后台恢复流程均不得回归。
