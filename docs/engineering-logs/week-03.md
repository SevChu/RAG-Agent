### 遇到的问题与处理

#### 二分/折半查找跨表述排名偏低

查询使用“二分查找”，资料主要使用“折半查找”。Dense 检索能够召回直接相关内容，但首条
直接相关结果仅为 Rank 4。该样本保留为计划日 2 候选集扩大和 Reranker 的重点对照项。

#### 复合问题只覆盖部分证据

Dijkstra 问题同时要求算法过程和时间复杂度，Top-5 对过程支持充分，但没有直接返回完整
复杂度结论。后续生成前必须拆分子问题并检查证据覆盖，不能用模型常识补齐缺失结论。

#### 练习题题干被高相关召回

栈/队列问题的 Top-4 均为判断题或选择题题干，其中包含故意设置的错误陈述。单靠 Dense
或 Reranker 无法判断其事实地位，后续需要：

- 增加正文、例题、题干、答案和代码等 `content_role`；
- 将语义相关性与事实证据资格分开评分；
- 对复合问题执行子问题证据覆盖检查；
- 引用只绑定合格证据，证据不足时部分回答或拒答；
- 将该样本纳入 `evidence_hit@5`、`unsafe_evidence_rate` 等固定回归指标。

| 简洁 | 通常 80～160 字，无标题，单段或最多 3 个单句短要点，只保留结论与核心依据 |

结构，并以“基于资料的推导”明确标识。允许组合、比较和演绎检索证据，但仍禁止引入资料

程序可以确定正文 `[n]` 是否对应本次提供给模型的真实证据，也能阻断不存在的编号和无引用
回答，但仅凭编号无法完全判断一句话是否被该 Chunk 语义支持。因此本日保留服务端强约束，

用户配置 `.env` 后，测试夹具中的 `Settings` 也继承了真实 `LLM_API_KEY`，使“未配置 Key”

打印或提交密钥值。

#### 有效正文引用被来源清单顺序误拦截

首轮风格复测时，真实模型返回“模型回答中的引用与引用清单不一致”。原校验要求正文引用
首次出现顺序与 JSON `used_source_ids` 顺序完全一致；模型即使正文使用 `[2]` 后 `[1]`，
也可能把清单整理为 `[1, 2]`，从而误伤实际有效引用。模型还可能使用 `[1, 2]` 组合格式，
旧正则只能识别单独的 `[1]`。

修复后，服务端以用户真正看到的正文引用为唯一来源依据，按正文首次出现顺序去重并绑定
引用卡片；支持半角逗号、中文逗号和顿号组合引用。JSON 来源清单排序不同、遗漏或重复不会
导致失败，因为该冗余清单本身不增加引用安全性。正文引用不存在的编号或完全没有引用时
仍然拦截，因此核心安全边界没有放松。

2. `LLM_MODEL` 只作为页面首次加载默认值，模型选择不修改 `.env`，也不需要重启后端；
3. 历史引用保存完整快照，而不是只保存 Chunk ID，避免资料或索引变化后旧回答无法追溯；
4. 课程会话的事实范围始终由 `course_id` 决定，切换课程会退出当前会话并回到新会话状态；
5. 历史助手回答不能成为事实证据；本日完全不把历史注入 RAG，从产品文案上明确标识“回答
   仍逐题检索”，避免把持久化误解为上下文记忆；
6. 快速对话与课程会话共用可扩展的数据枚举，但本日只开放课程会话 API，快速对话继续由
   计划日 5 实现。

### 遇到的问题与处理

#### 正式迁移与验收进程写权限不同

正式 `app.db` 的 Alembic 迁移在获得写入授权后成功完成；但 Codex 浏览器验收所启动的长期
沙箱后端在命令让出控制权后只能读取正式 SQLite，创建会话会返回只读数据库错误。该限制
不来自应用权限设计，也没有造成半迁移或资料损坏。处理方式是：正式库只执行一次受控迁移，
写入行为由临时数据库 API 集成测试覆盖，浏览器只验证模型控件和页面状态；验收进程及临时
数据库副本随后全部停止和清理。用户正常从 PowerShell 启动的后端不使用该沙箱身份。

#### 保存历史不等于理解上下文

页面现在可以连续追加并恢复消息，但每个问题仍以原始问题独立检索和回答。界面顶部明确显示
“会话已持久化 · 回答仍逐题检索”，避免用户用“它”“这个算法”等指代问题验收日 4 后误以为
上下文功能失败。指代改写、有限历史窗口和 SSE 是计划日 5 的首要任务。

#### 验收时再次出现“无法连接到后端服务”

用户正式验收时前后端窗口均已打开，但页面仍提示无法连接。检查发现 8000 端口同时存在两套
FastAPI 监听：PID `21696` 是 22:25 启动且未完全退出的 Codex 验收残留，PID `33168` 是用户
22:43 正常启动的新后端。Windows 会把请求分配给两套监听，其中旧进程无法写入正式 SQLite，
因此页面表现为间歇性连接或写入失败。

仅结束旧验收进程及其子进程，保留用户的新后端和前端。清理后 8000 端口只剩 PID `33168`，
5173 端口只剩当前前端；健康接口、CORS 预检均正常。随后创建并删除一条专用测试会话，确认
正式数据库写入和删除成功，测试记录已清理。该问题属于验收进程清理不彻底，不是会话代码、
API Key、数据库迁移或用户启动命令故障。

### 完成内容

#### 有限上下文与 Query Rewriter

- 课程助手只读取当前会话最近 6 条、最多 6000 字符的已完成消息；快速对话使用独立的
  最近 10 条、最多 8000 字符窗口；
- 首轮问题不额外调用改写器；存在历史时，Query Rewriter 输出可独立检索的 JSON 查询；
- 检索使用改写后的查询，回答继续面向用户原始追问；改写查询只用于理解指代，不作为事实证据；
- 每次课程回答保存原始问题、改写查询、上下文消息数和是否发生改写，便于人工验收与回归；
- 历史助手回答只能帮助消解指代，任何最终结论仍必须通过当前课程证据门、引用校验和拒答规则。

#### SSE 与中断语义

- 课程助手新增 `POST /api/courses/{course_id}/answers/stream`，快速对话新增
  `POST /api/quick-conversations/{conversation_id}/messages/stream`；
- 两条流均定义 `start`、`delta`、`complete`、`error`；课程回答额外定义 `citations`；
- 课程正文先通过证据充分性和引用一致性校验，再作为 `delta` 发送，避免把未校验文本显示为
  可信课程答案；
- 页面提供“停止生成”，中断或失败的临时片段明确标记“未保存”，不会写成 `completed` 消息；
- 上游超时和领域错误通过 SSE `error` 返回，保留原有非流式课程接口用于兼容和回归。

#### 快速对话与双历史

- 启用快速对话的真实消息发送、共享模型选择、SSE、刷新恢复和删除；
- 快速对话使用 `ConversationKind.QUICK`，不绑定课程、不检索 Qdrant、不写入课程上下文；
- 侧栏“最近对话”只显示快速对话，“学习助手对话”只显示课程会话；两类记录均可进入和删除；
- 快速对话页面明确标注回答来自模型一般能力，不把内容伪装成课程知识库结论，也不在本周
  调用第四周的外部资料搜索。

### 关键设计与边界

3. 课程助手采用“先校验、后流式展示”，因此检索和模型生成阶段会先显示状态，正文开始出现时
