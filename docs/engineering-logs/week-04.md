## 周目标

本周在第三周课程 RAG、会话和 SSE 基础上，将学习助手从单一问答链路扩展为可自动识别任务、
按需调用外部信息并生成课程总结的 Agent。实现顺序强调先建立来源契约和失败边界，再接入
LangGraph 条件编排，最后扩展总结与出题，避免把联网、总结和组卷同时塞入一个不可验证的
生成节点。

本周计划覆盖以下能力：

1. 建立课程资料与外部来源的双命名空间引用、搜索状态和持久化契约；
2. 依据课程证据覆盖程度决定是否搜索，生成可核验的混合答案；
3. 在外部搜索失败时保留已有课程回答，并显式说明降级状态；
4. 从同一课程对话入口自动路由普通问答、课程总结和后续出题任务；
5. 总结始终受课程证据约束，并能依据用户真实目标改变内容结构；
6. 在总结契约稳定后接入混合组卷、来源比例和编程语言规则。

## 周验收标准

- “仅课程资料”模式绝不调用 Web Search，混合模式也不会对所有问题无条件联网；
- 混合回答中的 `[课n]` 与 `[外n]` 均可回到真实来源，不接受模糊或越界引用；
- 外部服务超时、HTTP 5xx、无合格来源时不会拖垮课程已经能够回答的部分；
- 同一对话输入框能自动区分普通问答和总结，且路由结果、范围与诊断可随历史消息恢复；
- 总结只使用课程资料，明确的总结方向不会被统一模板稀释；
- 出题默认 20 题、语言每次可选且默认偏向 C++，课程改编题不超过 30%，外部补充题不超过
  20%；
- 每个计划日分别通过后端测试、静态检查、前端测试与构建，并提供可由用户复现的验收入口。

### 关键设计与决策

1. **先固化来源契约，再接入生成链路。** 外部搜索结果只有进入独立的 `external` 来源空间后
   才能交给生成器，避免计划日 2 再修改所有响应和历史消息结构。
2. **课程与外部引用独立编号。** `[课1]` 与 `[外1]` 可以同时存在，用户无需根据一张混排清单
   猜测某个编号属于教材还是网络。
3. **真实 URL 是外部证据的最低门槛。** 模型生成的来源名称、记忆中的网页或无法与工具结果
   对齐的摘要均不接纳，防止“看起来像引用”的内容进入答案。
4. **质量筛选采取允许类别加低质量过滤。** 学术、大学、科研机构、标准组织和官方文档优先；
   论坛、自媒体和聚合页不因标题相关就进入合格证据。
5. **旧会话按课程范围解释。** 新字段存入现有 JSON 快照而不是立即迁移数据库，缺失字段时
   采用第三周语义，确保历史记录仍可打开。
6. **计划日边界必须在界面可见。** 范围选择器可以先落地，但页面明确说明本日尚未将搜索
   接入正式答案，避免把基础设施误认为已经完成混合问答。

### 问题及处理

#### 外部搜索响应正文不可直接作为公开证据

服务端工具返回的搜索正文包含不可直接读取的加密内容块，不能把模型随附的文字自动当作网页
原文。适配器因此把“工具给出的真实 URL”和“同次响应生成的摘要”分开处理：仅当摘要声明的
URL 能与工具结果严格对齐时才接纳，并在界面中明确标为证据摘要而非逐字网页摘录。

#### 真实服务偶发 HTTP 503

验收搜索时出现过一次 HTTP 503，重试后成功。这不是课程资料或前后端入口错误，而是上游服务
暂时不可用。计划日 1 将其转换成结构化 `failed` 状态并隐藏敏感响应；计划日 2 再依据这一状态
完成课程答案降级。

#### 新范围选择器可能造成能力误读

前端已经能选择“课程资料 + 外部补充”，但本日尚未把搜索结果送入生成器。为避免用户误以为
答案已混合联网内容，界面增加阶段说明，验收标准也明确计划日 1 不检查正文 `[外n]`。

- 最终引用列表以正文实际使用且校验通过的编号为准，不把未使用结果全部展示成答案来源。

#### 失败降级与可观测性

- 搜索超时、HTTP 错误、无合格来源或适配器异常时不直接终止问答；
- 存在合格课程证据时回到课程生成并记录 `fallback_applied=true`，否则保持证据不足拒答；
- 前端展示条件搜索原因、合格与采用来源数、安全降级提示、来源差异状态和外部引用链接；
- 搜索判断、失败原因、采用数量和冲突标志随回答写入会话快照，无需数据库迁移。

### 关键设计与决策

1. **搜索决定由可解释规则完成。** 当前不为“是否联网”额外调用一次 LLM，控制响应成本和
   不确定性；阈值通过配置暴露，留待第五周评测数据校准。
2. **`course_only` 是硬隔离而非提示词偏好。** 该范围从图的条件边直接绕过搜索节点，即使
   用户问题中写有“联网”“最新”，搜索网关也不会被调用。
3. **外部搜索是补充而非替代。** 课程证据足够时默认不搜索；进入混合分支后也同时保留课程
   来源，避免最新网页内容静默覆盖教材口径。
4. **失败降级取决于证据资格。** 只有已经通过 Reranker 与内容角色安全门的课程证据才能支撑
   降级答案，不能因外部服务失败而降低第三周建立的证据门槛。
5. **冲突展示采用“模型识别、服务端约束”。** 语义冲突交给生成模型判断，但一旦声明存在
   差异，服务端强制检查“资料差异”段和双方引用，防止只给结论不展示依据。
6. **诊断信息进入持久化快照。** 历史回答不重新运行搜索；刷新后展示当时的决定、来源与失败
   状态，保证验收结果可追溯。

### 问题及处理

#### “混合模式”容易被误解为每次都搜索

产品目标是允许外部补充，而不是固定串行调用 Web Search。实现将课程覆盖、显式联网意图和
时效性拆成条件，并把判断原因显示给用户；因此同一个“课程资料 + 外部补充”设置下，课程内
问题可以完全不联网，资料缺口或最新信息问题才联网。

#### 外部搜索失败不能与“无资料”混为一谈

HTTP 503、超时、没有合格来源和根本未请求搜索具有不同语义。状态模型保留这些区别，状态图
再结合课程证据决定降级或拒答，避免上游短暂故障被错误显示成课程知识库缺失。

#### 双命名空间引用增加了校验分支

模型可能继续输出旧 `[n]`，也可能引用未采用的搜索结果。生成服务集中解析两类标记、检查
边界并按正文重建引用清单；前端只消费已校验结果，不自行猜测来源类型。

#### 来源冲突不能只靠固定关键词判断

课程与当前官方资料的差异可能以多种方式表达，纯规则无法可靠识别。当前由模型返回冲突声明，
服务端只验证展示形式和引用完整性；该边界被明确记录，后续可用冲突评测集继续增强。

### 当日目标

解决的不是“再增加几类总结模板”，而是总结系统如何理解任意方向的问题。计划日 4 将路由器、
总结 Planner、分节检索、受约束生成和质量校验拆开：用户给出明确方向时，系统围绕该方向生成
专属结构；请求模糊时才采用稳定的综合总结。完成这一基础后，出题分支才能复用相同的“规划—
取证—生成—校验”模式，而不继承固定八段契约。

### 实施目标

- 从根本上移除“所有总结都填充固定八段栏目”的生成方式；
- 不建立持续膨胀的总结意图枚举表，而是从用户原始要求中动态提取总结目标、关注方向、受众、
  详细程度、组织方式、必须包含项和排除项；
- 继续保持总结仅使用课程资料、`[课n]` 引用校验、自动路由和历史会话兼容；
- 本阶段完成并验收后，再在同一请求路由中接入出题分支，避免连续重构路由与生成契约。

### 计划实施顺序

1. **动态总结规划**：新增受 Pydantic 约束的 `SummaryPlan`。路由器只判断是否为总结任务，
   Planner 负责解析范围、目标、开放式关注方向、受众、粒度、篇幅、输出形式、包含/排除条件，
   并生成数量和标题均可变化的章节计划；不把关注方向限制为预置三选一或有限枚举。
2. **固定外壳、动态正文**：将当前固定八字段结果改为稳定元数据加动态 `sections[]`；每个章节
   至少包含标题、写作目的、正文和采用的课程证据编号。只有“总结第三章”一类模糊请求才回退
   到默认综合结构，明确请求不得为了凑模板强行加入无关栏目。
3. **按章节定向检索**：Planner 为各章节生成独立检索目标和查询，不再让所有栏目只共享一次
   通用 Top 12。检索结果仍经过现有 Reranker 与内容角色安全门；证据不足的章节明确提示限制，
   不使用模型记忆补齐。
4. **受约束的分段生成**：生成器严格按计划逐节组织内容，允许提纲、对比、流程、清单、问答等
   Markdown 结构；代码和公式仅在用户明确要求或课程证据确有必要时出现。
5. **去同质化与质量校验**：服务端检查用户要求覆盖率、各章节证据覆盖、`[课n]` 越界/模糊/
   外部引用、未请求的通用内容以及章节间重复度。覆盖不足或重复度过高时只重写问题章节，并为
   重试设置上限；不能修复时返回具体限制，不返回伪合格总结。
6. **交互与持久化**：前端继续复用课程对话输入框，按动态章节渲染；会话快照保存总结计划摘要、
   实际章节和校验诊断，Day 3 的固定结构历史消息仍能正常打开。
7. **测试与文档**：补充 Planner、动态结构、定向检索、引用安全、重复校验、失败降级、历史兼容
   的单元与 API 测试，并在完成时新增计划日 4 验收文档。

### 关键设计与决策

1. **总结意图保持开放字段。** Planner 可以提取“从工程取舍角度总结”“只整理反直觉结论”等
   未预注册方向，不把目标限制为知识点、考点、代码等有限枚举。
2. **结构稳定性放在外壳而非栏目。** API 保留任务类型、范围、诊断和 `sections[]`，章节标题、
   数量、目的和组织形式按请求变化；前端因而无需为每一种新方向增加组件分支。
3. **规划不能代替证据。** Planner 负责决定应写什么，课程检索负责证明能写什么；某个章节
   找不到材料时显示局部限制，不能用模型记忆补齐计划中的空白。
4. **各章节拥有独立检索目标。** 一次通用 Top 12 容易让所有总结依赖相同片段并趋于同质，
   因此计划中的章节分别检索、重排，再由服务端统一编号和去重。
5. **质量校验关注需求覆盖与重复，而不只检查 JSON。** Pydantic 只能保证字段存在，无法证明
   回答真正围绕用户方向；计划增加包含/排除约束覆盖和章节间重复检查。
6. **局部修复优先。** 单节证据不足、遗漏约束或重复过高时只重写问题章节并限制次数，避免
   全文重生成导致原本合格内容和引用漂移。
7. **继续坚持课程证据硬边界。** 动态结构不会放宽 `course_only`、`[课n]` 或 Web Search
   隔离；“更灵活”只指总结目标和表达结构，不指事实来源。

### 风险、边界与处理原则

#### Planner 输出合法但理解错误

结构化输出只能证明字段格式正确。实现时还需把用户原句、必须包含项和排除项保留到校验阶段，
并检查每项是否落入至少一个章节；否则“合法 JSON”仍可能生成错误方向的总结。

#### 分章节检索导致延迟与重复证据增加

每节单独检索能改善针对性，但不能无限增加检索与生成调用。实现时限制章节数、复用本地检索
组件、合并重复 Chunk，并优先采用一次规划、若干本地检索和一次结构化生成；只有失败章节才
产生有限重试。

#### 动态结构破坏历史消息展示

Day 3 已保存固定八段 Markdown，不能要求用户重建会话。前端和快照解析会同时支持旧正文与新
`sections[]`；本计划不通过回写数据库来“升级”旧消息。

#### 过度追求差异造成内容失真

去同质化不是要求每次使用花哨版式。模糊请求仍应稳定、相似课程证据仍可能产生部分相同结论；
验收关注的是用户明确方向是否改变章节和重点，而不是机械规定标题必须完全不同。

### 开发中发现的问题与处理

1. 当前 `LLM_MAX_OUTPUT_TOKENS=1600` 不适合一次返回 20 道完整题，尤其编程题字段较长。改为
   题型加权分批，最终仍由服务端组装和整卷校验。
2. 真实 DeepSeek 对合法语义返回 `null` 列表、布尔判断答案、`"课1"` 和 `course` 等表示，
   两次严格解析都失败。改为只归一化可由槽位与命名空间安全推导的字段，不放宽来源或数量。
3. 合成材料首轮虽然配额和引用通过，但答案加入来源未写出的线性结构和顺序队列复杂度。新增
   整卷证据审查和局部重生成，不再把“有引用”误当作“受引用支持”。
4. 加强审查后真实模型的多题修复 JSON 被截断。将修复批次缩小并增加一次紧凑重试。
5. 真实模型生成第 4、5 题近似重复。将重复题也纳入局部修复，而不是要求用户整卷重试。
6. 只有一段栈/队列材料却要求 5 道含困难题时，修复后仍有无依据内容，系统按设计拦截整卷；
   缩小到 3 题后真实模型正常生成并通过结构、来源、重复和证据审查。
7. 开发侧尝试对本地真实课程执行额外外发审计时，安全策略要求单独的数据外发授权。没有绕过；
   改用不含用户资料的合成材料验证真实模型，实际课程质量交由用户在应用内主动验收。
8. 用户首次实际验收输入“根据当前课程生成一份试卷，先不用给答案和解析”，系统在第 18 题
   报“缺少答案”。根因是确定性计划只识别“不要答案”等少量否定短语，未覆盖“先不用给”这类
   常见表达，导致整卷仍按含答案模式生成和校验。现已扩展答案/解析否定表达，覆盖“先/暂时不用”、
   “无需/不需要提供”、“答案不用给”、“仅题目”等语序；并分别增加用户原句计划测试与模型
   完全省略答案、解析时的端到端生成测试，防止只修解析结果而遗漏后续校验与渲染。
9. 用户第二次实际验收输入“请根据第三章的内容出一份单元试卷，但不要答案和解析”，收到的却是
   “混合回答格式”错误。该错误证明请求没有进入出题分支，并非试卷证据门或格式门过严。根因是
   路由只覆盖“生成试卷”“组卷”“出 20 题”等表达，漏掉“出一份单元试卷”。现已将生成、制作、
   设计、编制、拟定、出等动作与试题、试卷、卷子建立有界搭配，同时保留纯名词问句为普通问答；
   用户原句路由测试和同类课程回答 API 集成测试均已补充，后者还断言最终正文不含答案、解析。
10. 用户第三次实际验收输入“请给出一份有关于栈相关知识点的试卷，不用提供答案和解析”，在已经
    完成长耗时的默认 20 题生成后，因第 19 道编程题缺少输入输出、约束、样例或测试设计而整卷失败。
    这里同时存在边界和恢复粒度问题：无答案学生卷不展示参考代码、复杂度和测试设计，却仍把测试
    设计列为硬必填；批次解析成功后又未立即检查这些字段，直到整卷阶段才暴露。现将输入、输出、
    约束和样例保留为编程题题面硬字段；含解析时才要求复杂度和测试设计；每个生成批次解析后立即做
    字段检查，不合格时携带具体原因仅重试该批次。用户原句路由和“首次缺样例、局部重试后成功”
    的端到端测试均已补充。无答案模式的内部教师解答策略随后由第 15 项缺陷修复替换。
11. 用户第四次实际验收输入“请根据第三章的内容出一份模拟卷，但只要答案，暂时不用输出解析”，
    返回资料不足。直接执行路由与计划解析确认：输出开关已正确得到“含答案、不含解析”，但任务被
    判为 `question`；原因是路由词表只有“模拟试卷”，没有“模拟卷”。鉴于连续发生同义短语漏判，
    本次不再添加单个特例，而是抽象“出题动作 + 卷类产物”：统一覆盖试卷、卷子以及模拟、单元、
    章节、期中、期末、综合、练习、测试、随堂和复习卷，并支持生成、制作、设计、编制、拟定、出、
    给出、来一份等动作。另增加问句排除门，使“如何设计模拟卷”“组卷原则是什么”等仍走普通问答。
    用户原句路由测试及“模拟卷只要答案”的 API 集成测试均通过，后者确认正文有答案而无解析。
12. 用户用同一条“模拟卷只要答案”请求复验后进入了出题分支，但第 18 题报“缺少答案”。默认卷
    第 18～20 题为编程题；现有契约同时要求独立 `answer` 文本和 `reference_code`，真实模型即使
    已提供参考代码，也可能将重复的答案摘要留空，局部重试后仍被通用答案门拦截。本次将编程题的
    参考代码确认为可执行答案主体：参考代码存在且其余教师版字段合格时，空答案摘要确定性规范为
    “见参考代码”，但参考代码本身仍是硬要求。进一步按用户语义拆分输出边界：只要答案时保留答案
    摘要和参考代码，不生成、不校验、不展示属于解析的复杂度与测试设计；要求解析时才恢复这两项。
    新增“编程题有代码但答案摘要为空”的端到端回归，确认最终有答案和代码、无解析相关内容。
13. 用户再次复验同一请求时，第 5 题报“选择项少于 4 个”，并明确要求一次处理所有可能问题。
    这暴露出此前虽然增加一次批次重试，仍把模型输出假定为稳定 JSON 列表，且来源错误和部分比例
    错误仍会拖到整卷阶段。本次建立统一结构自恢复层：支持围栏/说明文字包裹 JSON、`items` 与常见
    字段别名、选项对象、单字符串选项、题干内 A/B/C/D、答案数组和来源别名；每批次立即校验选项、
    输出开关、编程字段、引用范围及外部槽位，失败时携带精确原因最多局部修复 3 次。修复批次也走
    同一入口，证据审查 JSON 增加围栏、别名和最多 2 次格式重试；教材改编超额不再立即整卷失败，
    而是把超额题与所有重复题一起局部改写。新增完整默认 20 题故障注入，刻意让第 5 题首次只有
    3 项、让第 18～20 题只有参考代码，最终自动恢复为 20 题合格答案卷。结构恢复矩阵 24 项、后端
    全量测试均通过。
14. 为避免继续依赖用户试错，开发侧使用 10 段不含用户资料的合成“第三章·栈”材料和真实
    `deepseek-v4-flash` 连续审计默认 20 题。审计依次暴露：修复后重复题仍被第二次校验直接拦截；
    证据审查载荷遗漏选择项，导致只看到答案字母却无法核验；`0.90` 单一题干相似度误判公共模板；
    低随机性模型对少数重复题多轮改写仍不变化。对应修复为：内容问题最多 3 轮重算；审查载荷加入
    完整选项并按“正确答案可由来源明确支持或有限确定性推导”检查，不要求错误干扰项为真；重复题
    改用题干 `0.97` 加知识点 `0.90` 双条件；重复只强制改写一轮，若证据和来源均已通过则带具体
    题号警告返回。最终真实审计在约 122 秒内返回 20/20 题，答案开启、解析关闭、题型难度完全匹配，
    来源与证据审查通过；模型未改开的第 5、6 题以可见警告返回。真实审计还说明多轮重复改写会把
    token 用量推高到约 5.2 万，因此最终性能规则不再为纯重复问题执行三轮。
15. 用户改用“请根据书中排序章节出一份模拟卷，但答案和解析都不要”，15 道题经过 3 轮内容修复
    后仍被判证据不支持。根因不是排序材料必然不足，而是无答案计划在整卷证据审查之前就把生成结果
    的 `answer` 和 `reference_code` 清空；审查器随后被要求验证一个不存在的正确答案，局部修复生成
    的答案又在每轮归一化时被清空，形成无法收敛的循环。同时，组合语序“答案和解析都不要”没有被
    输出计划识别，可能错误开启两个输出项。现将内部教师答案与用户可见输出彻底分离：每题始终生成
    并校验内部答案，编程题保留内部参考代码；Markdown 渲染只在 `include_answers=true` 时展示，
    因而用户正文不会泄露答案或代码。缺少内部答案/代码成为批次级可恢复错误；组合否定语序也纳入
    确定性计划解析。新增用户原句默认 20 题回归，确认审查载荷含内部答案而最终正文答案、解析和代码
    均为 0。另以 10 段纯合成排序材料调用真实 `deepseek-v4-flash`：约 91 秒返回 20/20 题，答案与
    解析关闭、证据审查通过、正文答案/解析标记均为 0，总用量 31133 tokens；第 5～8 题的近似重复
    按既有软质量策略警告返回，没有再因证据误判拦截整卷。

### 用户首轮验收：前端监听地址不一致

用户按第五日说明启动前后端后，浏览器访问验收网址立即提示“拒绝连接”。本机只读诊断显示后端
正常监听 `127.0.0.1:8000` 且 `/api/health` 返回 200；前端进程却只监听 IPv6 回环地址
`::1:5173`，而第五日文档要求打开 IPv4 地址 `http://127.0.0.1:5173/assistant`。因此请求尚未
到达 Vue 或后端，与 Agent 分支无关。

根因是第五日启动命令简写为 `npm.cmd run dev`，同时 `vite.config.ts` 没有固定开发服务器地址；
当前 Windows/Node 环境把 `localhost` 解析为 `::1`。现将 Vite 默认开发服务器固定为
`host=127.0.0.1`、`port=5173`、`strictPort=true`，并把第五日命令恢复成带显式
`--host 127.0.0.1` 的形式。这样默认命令与文档 URL 双重一致，5173 被占用时也会明确失败，
不会静默换端口后继续让用户访问错误地址。

### 用户第二轮验收：三道单选题反复缺少第四项

用户发送 `请根据排序章节出一份仅含3道单选题的模拟卷。`，第 1 题在三次局部修复后仍报选择项
少于 4 个。现有恢复层可以解析选项对象、字符串和题干内 A/B/C/D，但当低随机性模型反复只给
A/B/C 时只会重新请求同一道题，没有可证明安全的本地恢复。

本次没有添加无限重试，也没有凭空生成课程事实。对于单选或多选题，只有同时满足“规范化后恰好
3 项”和“内部答案明确指向至少一个现有 A/B/C 选项”时，服务端补入
`D. 以上选项均不正确`。由于已有正确项位于 A/B/C，D 可由命题逻辑确定为错误干扰项，不依赖
课程外知识；答案指向缺失 D、无法解析或少于 3 项时仍执行原有有界重试并最终拦截。单选、多选、
文本答案和不安全答案路径均有回归。

首次真实复测通过了四项结构门，却继续暴露第 1 题三轮内容修复后证据不支持。审查提示虽说明
错误干扰项不必为真，但不知道 D 是服务端补项；内容修复器也可能在解析中加入来源未写明的事实。
修复后，审查载荷显式列出 `system_completed_option_labels`，不得仅因逻辑干扰项未见于教材拒绝；
内容修复必须锚定一条课程来源，同步改写题干、答案、解析与来源编号，解析不得扩写复杂度、实现或
比较结论。最终错误也会携带具体不支持详情，不再只有题号。

沿用同一 token 账本再次运行用户原句，约 15.58 秒返回 3/3 单选题，答案和解析默认开启，3 个
课程引用、四项选择、来源比例、重复检查和逐题证据审查全部通过，无质量警告。此次之后保守累计
668,008 tokens，上游报告 120,472，仍低于用户批准的 1,000,000 上限。

### 用户第三轮验收：试卷答案续问被误路由为混合回答

用户在同一课程对话中先发送“请根据队列相关内容出一份仅含3道判断题的试卷，答案和解析都
不要”，第一轮正常；随后发送“现在给出答案和解析”，却报“模型没有按混合回答格式返回结果”。
检查确认这是两个相互关联的上下文缺口：任务路由在读取历史之前只判断本轮短句，第二句没有
“试卷/出题”等关键词，因而进入普通问答；同时第一轮虽已在内部生成并通过证据审查的教师答案，
持久化时只保存无答案 Markdown，后续即使纠正路由也无法保证回答同一组题。

修复采用“紧邻任务门 + 私有试卷工件”，没有把所有历史文本塞给路由器，也没有新增数据库列：

1. 只有最新一条已完成助手消息明确为 `exam`，且当前短句包含“给出/补充/显示答案或解析”等
   输出动作时，才视为试卷续写；“答案和解析有什么区别”之类普通问题不会触发；
2. 新试卷把完整、已校验的题目和教师答案写入消息 `retrieval` JSON 的私有 `_exam_artifact`。
   对外 `AnswerRetrievalRead` 会忽略该键，因此首轮回答、SSE complete 和历史 API 均不泄露答案；
3. 第二轮直接用同一工件重渲染输出开关，不重新检索、不重新调用模型、不修改题目；计划、质量、
   引用和四条历史消息继续持久化，检索模式标记为 `exam_artifact_replay`；
4. 对修复前没有私有工件的旧试卷，兼容路径读取上一轮可见题目和当时保存的课程证据，生成按原
   题号排列的答案页，并明确禁止另出新题；它仍受课程引用编号校验约束，不再进入混合回答解析器。

自动回归同时覆盖新工件零调用回放、旧会话兼容、独立“答案和解析区别”反例和隐私字段隔离。
后端全量 215 项测试、Ruff 和 Mypy strict 通过。使用当前真实“数据结构”课程与
`deepseek-v4-flash` 运行用户两段原句：第一轮生成 3/3 队列判断题且隐藏答案；第二轮 1.69 ms
恢复同一组三题，答案和解析各 3 处，题目正文逐题一致，历史为 4 条，第二轮 token 用量为 0。
选择性审计后账本为保守 `697,998 / 1,000,000`、上游报告 `125,570`、剩余 `302,002`，共
36 次有报告调用；临时审计对话已删除。

## 验收后功能增量：独立会话默认联网（2026-08-10）

### 增量目标与范围

设置页 Token 统计验收后，用户指出“快速对话 / 独立会话”固定禁止 Web Search，导致模型一般

强制联网；普通寒暄、纯创作/文本转换和明确要求不联网的轮次应直接回答。

### 实际完成内容

1. `QuickChatRequest` 新增默认值为 `true` 的 `web_search` 字段。旧前端或直接 API 调用即使不传
   该字段，也默认获得自动联网能力；前端工具栏同时提供逐轮关闭开关，新建或刷新会话恢复开启。
2. 服务端对快速对话实施确定性自动路由：信息型问题默认搜索，寒暄、纯创作和否定联网指令跳过。
   该决策不额外调用分类模型，避免每轮先产生一次不可见 Token 和延迟。
3. 指代型追问会把最近一条用户消息作为搜索背景，例如“它现在稳定了吗”能够与上一轮主题共同
   构成查询；普通独立问题保持原查询，不执行额外 LLM 改写。
4. 搜索成功时，将现有外部搜索网关返回的标题、发布者、URL 和摘要作为不可信证据注入最终生成，
   提示模型用 `[外n]` 标注。搜索状态与来源写入助手消息，刷新后仍可恢复并点击来源卡片。
5. 快速回答采用宽松而安全的引用后处理：保留有效 `[外n]`，移除不存在的编号，但不会像课程
   严格证据链一样因单个引用格式错误拦截整轮临时对话；实际引用数单独写入搜索诊断。
6. 搜索超时、HTTP 503 或没有合格结果时，最终生成继续执行，提示最新信息可能不完整，并把失败
   原因和 `fallback_applied=true` 持久化。该轮不会再次退回“快速对话失败，请重试”的笼统错误。
7. 快速对话继续不读取课程资料、不写入课程历史。搜索调用和最终生成调用均由已有底层 Token
   记录器按实际响应模型累计，无需新增统计旁路。

### 关键设计决策

- “默认支持联网”落实为默认开启的自动路由，而不是每条消息都强制搜索。这样最新信息问题能够
  获得新证据，`你好`、翻译和创作任务不会承担无意义的搜索延迟与 Token。
- 搜索决策同时由请求开关、服务端总开关和用户本轮否定指令约束。前端开关改善可见性，但后端
  始终独立执行规则，不能依赖前端正确传参来维持边界。
- 复用计划日 1～2 已验证的外部搜索适配器、来源质量门和敏感信息保护，不另建一套直接抓网页的
  快速通道；来源口径和 Token 统计因此与课程混合回答保持一致。
- 联网元数据复用消息现有 `retrieval` JSON，模式标记为 `external_web`，不新增数据库迁移。该数据
  需要随回答回放，但当前没有按搜索状态进行独立数据库查询的需求。
